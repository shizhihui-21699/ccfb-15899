# 部署与运行

## 一、角色与信任边界

系统涉及两方，密钥严格分离：

| 角色 | 运行位置 | 持有 | 职责 |
|---|---|---|---|
| 省级律师管理平台 | 外网/政法专网 | **私钥** | 导出律师名册、在押人员、预约名单，签名后生成导入包 |
| 看守所窗口机 | 内网，不联网 | **公钥**、本机窗口密钥 | 导入、核验、授权、留痕 |

> 私钥一旦泄露，任何持有者都能伪造"某人是合法执业律师"的名册。看守所侧永远只登记公钥。

## 二、首次部署

### 1. 安装运行时

窗口机建议 Windows 10/11 x64，安装 .NET 11 Desktop Runtime。
程序本身是 Avalonia，也可在国产 Linux 桌面（麒麟/统信）运行，需对应运行时。

```bash
dotnet publish src/DetentionVerify.Desktop \
  -c Release -r win-x64 --self-contained true \
  -p:PublishSingleFile=true -o ./publish
```

`--self-contained` 可省去预装运行时，代价是体积较大；政务机器上通常更省事。

> **发布后必须实测启动一次。** 项目文件里已设置
> `IncludeNativeLibrariesForSelfExtract=true`，把 SQLite 等原生库嵌进单文件。
> 若手工删除该设置，发布目录会只剩一个 exe，拷到窗口机后程序在启动瞬间
> 因 `DllNotFoundException: e_sqlite3` 崩溃——开发机上因为 dll 就在旁边，不会暴露。
> 崩溃信息会写入 `<数据目录>/logs/crash.log`。

### 2. 数据目录

默认 `%LOCALAPPDATA%\DetentionVerify\`：

```
detention-verify.db      主库（含名册、流水、审计）
detention-verify.db-wal  WAL 日志（勿删）
settings.json            窗口号、民警、窗口密钥（权限已收紧）
exports/                 备查包
```

用环境变量指向受控/加密盘：

```powershell
setx DETENTION_VERIFY_DATA "D:\看守所数据\detention-verify"
```

**必须备份** `detention-verify.db` 与 `settings.json`。`settings.json` 里的窗口密钥丢失，
监区侧已签发的当日授权码将无法校验。建议纳入每日备份与异机副本。

### 3. 登记签名公钥

启动程序 → `Ctrl+Shift+A` → "签名公钥"区：
- 密钥编号：与省级平台约定的编号（如 `prov-key-2026`），**必须与包内 manifest 的 keyId 一致**
- 公钥：粘贴 `prov-key.pub.pem` 全文
- 有效期（可选）：到期后导入会被拒绝，避免长期使用过期密钥

### 4. 首次导入

管理窗口 → 选择导入包目录 → "校验并导入"。

会依次校验：签名 → 清单哈希 → 律师名册哈希 → 在押名册哈希 → 预约哈希（如声明）→
数量一致 → 证号无重复 → 批次序号单调。

任何一步失败，**当前名册原样保留**，窗口可继续工作。

## 三、日常运行

### 名册同步节奏

建议每日开所前导入一次。界面顶部常驻显示名册时效：

| 状态 | 含义 | 系统行为 |
|---|---|---|
| 正常（≤30 小时） | 数据新鲜 | 查无此人 → 禁止会见 |
| 偏旧（30–96 小时） | 需补数据 | 查无此人 → 禁止，但提示"可能是数据未更新" |
| 过期（>96 小时） | 数据不可信 | 查无此人 → **人工复核**，不直接判定伪造 |

阈值可在 `settings.json` 的 `rosterWarnHours` / `rosterDegradeHours` 调整。

### 窗口操作流程

1. 预约名单里点律师姓名 → 自动带入证号、姓名、在押人员、手续类型
2. 核对执业证原件与身份证，比对照片与本人
3. 按 `Enter` 核验
4. 根据结论：
   - **核验通过** → `F2` 签发授权码
   - **有疑点** → 填写放行理由 → `F2`
   - **须人工复核** → 另一名民警填写复核人与核实情况 → `F2`
   - **禁止会见** → 无授权按钮，报告值班领导
5. 将授权码交监区，监区离线核对后安排会见

### 授权码在监区侧如何校验

授权码 = `HMAC-SHA256(窗口密钥, 会话号|证号|在押人员号|日期)` 取前 60 位，Base32 编码。

监区终端需持有**同一窗口密钥**。校验时复算并比对，同时确认：
- 日期是当日（隔日自动失效）
- 在押人员编号与带人对象一致
- 该会话未撤销

跨窗口时各窗口密钥不同；若监区无法区分窗口，可将 `settings.json` 的 `windowSecret`
在多个窗口间设为同一值，或在备查包中按会话号检索。

## 四、备查与督查

管理窗口 → "导出备查包"，生成：

```
sessions-YYYYMMDD.csv    当日流水（含未授权查询）
audit-YYYYMMDD.jsonl     审计事件全量
README-YYYYMMDD.txt      记录数、链头哈希、文件哈希、复核方法
```

督查方独立复核方法（README 内亦写明）：
1. 按 `seq` 顺序遍历 `audit.jsonl`
2. 对每条计算 `SHA-256(上一条 hash + "\n" + 规范化 JSON)`
3. 与记录内 `hash` 比对；并核对 `prevHash` 等于上一条 `hash`

任何一条被改、被删，链在此处断开。

### 建议的外部锚定

哈希链能发现"事后改库"，但无法对抗持有整机管理员权限的人重算整条链。
建议每月将链头哈希（`README` 中的"链头哈希"）抄送上级机关存档，形成外部锚点。

## 五、故障处置

| 现象 | 原因 | 处置 |
|---|---|---|
| 顶部显示"尚无生效名册" | 未导入 | 立即导入；此前无法核验任何人 |
| 导入提示"密钥不在信任列表" | 未登记公钥 / keyId 不符 | 核对 manifest.json 的 keyId 与已登记编号 |
| 导入提示"序号低于当前" | 误用旧包 | 找最新包；确需回滚由管理员确认后操作 |
| 导入提示"哈希与清单不符" | 文件被改或拷贝不完整 | 重新拷贝完整包，勿手工编辑文件 |
| 审计链异常 | 库被改动 | 立即导出当前状态，报告上级并比对备份 |
| 授权码监区校验不通过 | 窗口密钥不一致 / 隔日 / 已撤销 | 核对 `settings.json` 与监区配置；确认日期 |

## 六、安全注意事项

- 窗口密钥、公钥文件、数据库均不应存放在共享目录
- `settings.json` 含窗口密钥，权限已限制为当前用户读写
- 导出的备查包含律师姓名、证号（不含身份证号原文），按内部资料管理
- 身份证号仅以加盐 SHA-256 存库，**不可逆**；如需按身份证号检索，只能比对后 6 位
- 数据库文件建议磁盘加密（BitLocker / 国产加密盘）
